├─────────────────────────────────────────────────────────────────────────────┤
│  THE SIMPLE STORY — JWT + COOKIES ON THIS SITE (memorise this first)      │
│  ─────────────────────────────────────────────────────────────────────── │
│                                                                             │
│  WHAT IS A JWT?                                                             │
│    A JWT (JSON Web Token) is a string the server creates when you log in.  │
│    It has 3 parts separated by dots:  Header.Payload.Signature             │
│      Header   — says which algorithm was used (HS256 here)                │
│      Payload  — holds your info: userId, username, role, expiry time      │
│      Signature — proves the server made it (HMAC with a secret key)       │
│    Anyone can read the Payload (it's just Base64). The Signature stops    │
│    anyone from faking or modifying it.                                     │
│                                                                             │
│  WHAT IS A COOKIE?                                                          │
│    A cookie is a small piece of data the server tells the browser to save. │
│    On this site the JWT itself is saved inside a cookie called             │
│    "ApiAccessToken". The key security settings:                            │
│      HttpOnly = true  → JavaScript cannot read it  (prevents XSS theft)  │
│      Secure = true    → browser only sends it over HTTPS                  │
│      SameSite = Lax   → browser won't send it on cross-site POSTs (CSRF) │
│      Expires = 1 hour → cookie (and JWT) expire after 1 hour             │
│                                                                             │
│  HOW THEY WORK TOGETHER ON EVERY REQUEST:                                 │
│    1. You log in → API creates a JWT → MVC saves it in the cookie.        │
│    2. You visit any page → browser sends the cookie automatically.        │
│    3. MVC reads the JWT from the cookie → attaches it as                  │
│       "Authorization: Bearer <token>" header when calling the API.        │
│    4. API validates the JWT signature and checks the Sessions table.      │
│    5. If valid → request proceeds. If not → 401 Unauthorized.            │
│                                                                             │
│  ─────────────────────────────────────────────────────────────────────── │
│  USER FLOWS TO TRACE IN THE CODE:                                          │
│  ─────────────────────────────────────────────────────────────────────── │
│                                                                             │
│  REGISTER (new account):                                                   │
│    User fills form → POST AccountController.Register (MVC)                │
│      → calls POST /api/auth/register                                       │
│      → AuthController.Register hashes password, saves to Users table      │
│      → role is forced to 1 (User) unless caller is admin                  │
│      → returns 201 Created                                                 │
│    MVC redirects to login page                                             │
│                                                                             │
│  LOGIN:                                                                    │
│    User fills login form → POST AccountController.Login (MVC)             │
│      → calls POST /api/auth/login                                          │
│      → API: finds user by email OR username, verifies password hash       │
│      → API: creates JWT (userId + username + role inside)                 │
│      → API: saves Session row in Sessions table (so logout works)         │
│      → API: returns { token, expiresAt } to MVC                          │
│    MVC: saves JWT in "ApiAccessToken" HttpOnly cookie                     │
│    MVC: also signs in with ASP.NET cookie auth (for [Authorize] on views) │
│    MVC: redirects to home page (or the page they were trying to reach)   │
│                                                                             │
│  LOGOUT:                                                                   │
│    User clicks Logout → POST AccountController.Logout (MVC)               │
│      → reads "ApiAccessToken" cookie, calls API to mark session inactive  │
│      → deletes the cookie from browser                                    │
│      → signs out the ASP.NET cookie auth                                  │
│      → redirects to home                                                  │
│                                                                             │

SECTION 0 — PROJECT OVERVIEW  [CRITICAL — read in Hour 1]
================================================================================

WHAT IS THIS PROJECT?
  XcelerateLinks is a professional networking platform (like a mini LinkedIn).
  It is built as TWO separate ASP.NET Core projects that talk over HTTP:

  A) APIPSI16  — the backend REST API (port 7263 / 5270)
     - Uses Entity Framework Core to talk to SQL Server
     - Secured with JWT Bearer tokens
     - Exposes endpoints under /api/...
     - Also hosts a SignalR hub for real-time chat (/hubs/chat)

  B) XcelerateLinks  — the frontend MVC web app (separate port)
     - Razor views (.cshtml) rendered server-side
     - Calls the API over HTTP using IHttpClientFactory
     - Secured with Cookie Authentication (ASP.NET Core Identity cookie)
     - The JWT token is stored in an HttpOnly cookie so the browser never
       exposes it to JavaScript

KEY FEATURES
  - User registration / login / password reset
  - User profiles with bio, education, work experience, skills, photo
  - Job opportunities posted by employers
  - Job application pipeline with stages (Applied → Review → Interview → Offer → Hired)
  - Interview scheduling (InterviewRounds)
  - Real-time messaging (SignalR ChatHub)
  - Connections (LinkedIn-style friend requests)
  - Notifications
  - Subscription plans (Free / Pro / Enterprise) with rate limiting
  - Match scoring: opportunities ranked by how well they fit the user's preferences

POTENTIAL PROFESSOR QUESTION:
  Q: Why are there two projects instead of one?
  A: Separation of concerns. The API can be replaced/upgraded independently.
     The MVC app is just a "thick client" — it never talks directly to the DB;
     it always goes through the API. This also means a mobile app could use the
     same API with zero backend changes.

ENTITY FRAMEWORK CONCEPTS TO KNOW:
  - DbSet<T>       : represents a table; you LINQ-query against it
  - HasKey()       : defines the primary key
  - HasForeignKey(): defines FK relationship
  - HasMaxLength() : sets column size
  - HasColumnType(): overrides EF's inferred SQL type (e.g. forces "tinyint")
  - HasColumnName(): maps a C# property to a differently-named DB column
  - HasDefaultValue/HasDefaultValueSql(): default on the DB side
  - .Include()     : eager-loads navigation property (generates SQL JOIN)
  - .AnyAsync()    : EXISTS check
  - SaveChangesAsync(): flushes tracked changes to DB in a single transaction
  - EntityState.Modified: marks entity as dirty so EF generates an UPDATE

POTENTIAL PROFESSOR QUESTIONS (DB):
  Q: What is the difference between LocationId and the Location text field?
  A: Location is a legacy free-text field (e.g. "Lisboa"). LocationId is a FK
     to a structured Locations table that also holds Region and Country.
     The structured version enables the MatchScoreHelper to compare regions and
     countries precisely. Both are kept for backward compatibility.

  Q: Why is RequiredJobRoleIds stored as a comma-separated string instead of a
     separate junction table?
  A: Trade-off. A junction table (OpportunityJobRoles) would be more normalized
     and allow direct SQL joins, but would require more complex queries and
     migrations. The comma-string approach is simpler to write and read in code
     but means filtering by role must be done in C# after fetching data.

  Q: What is the role of the Sessions table given that JWTs are already signed?
  A: JWTs are stateless — the server cannot "unsign" them before expiry.
     The Sessions table adds server-side revocation: on logout, IsActive is set
     to false and future requests with that token are rejected, even though the
     JWT itself is still mathematically valid.

WHAT TO WRITE DOWN:
  The .NET Minimal API top-level statements pattern. Key learning items:

LINE-BY-LINE KEY CONCEPTS:

  var builder = WebApplication.CreateBuilder(args);
    Creates the host and DI container.

  builder.Services.AddCors(...)
    CORS = Cross-Origin Resource Sharing.
    The API is on port 7263; the MVC app is on a different port.
    Without CORS, browsers block the cross-origin requests.
    AllowCredentials() is needed for cookies.

  builder.Services.AddDbContext<xcleratesystemslinks_SampleDBContext>(options => {
      options.UseSqlServer(defaultConn, sql => {
          sql.MigrationsAssembly(typeof(Program).Assembly.FullName);
      });
  });
    Registers the DbContext as SCOPED (one per HTTP request).
    UseSqlServer() points EF at SQL Server.
    MigrationsAssembly() — tells EF which assembly contains the Migrations
    folder. Important because EF defaults to the assembly where the DbContext
    lives; here we override it to the API assembly.

  builder.Services.AddSingleton<ITokenService, TokenService>();
    TokenService is a SINGLETON — one instance for the lifetime of the app.
    Safe because it has no mutable per-request state (only reads config).

  builder.Services.AddScoped<IPasswordHasher<User>, PasswordHasher<User>>();
    BCrypt/ASP.NET Identity hasher. SCOPED = one per request.

  builder.Services.AddScoped<ISessionService, SessionService>();
    Needs DbContext so must be SCOPED too (can't inject scoped into singleton).

  JWT configuration block:
    keyBase64 = from env var XCELERATE_JWT_KEY or appsettings Jwt:Key
    The key is BASE64-encoded (so it can safely go in a config string).
    Decoded to bytes, then wrapped in SymmetricSecurityKey.
    Validated with: ValidateIssuer, ValidateAudience, ValidateLifetime,
    ValidateIssuerSigningKey all = true.
    ClockSkew = 30 seconds (small tolerance for clock drift between servers).

  ctx.Database.Migrate()   (called at startup inside a scope)
    Applies any pending EF migrations automatically when the app starts.
    If the migration fails it logs the error but continues — the app might
    still work if the schema is already correct.

  Raw SQL safety-net for EmployerCandidateHistory columns:
    "IF NOT EXISTS ... ALTER TABLE ..."  run via ADO.NET (raw SQL).
    This is a workaround for missing migration history (migrations were run
    manually without the [Migration] attribute, so __EFMigrationsHistory is
    incomplete). The raw SQL check is idempotent — safe to run every startup.

  app.UseAuthentication() / app.UseAuthorization()
    ORDER MATTERS: Authentication must come before Authorization.
    Authentication = "who are you?" (reads the JWT, populates User.Claims)
    Authorization  = "are you allowed to do this?" (checks [Authorize] attributes)

  app.MapHub<ChatHub>("/hubs/chat")
    Registers the SignalR WebSocket endpoint.

POTENTIAL PROFESSOR QUESTIONS:
  Q: What is Dependency Injection and why does it matter here?
  A: DI is a pattern where objects receive their dependencies from outside (the
     DI container) instead of creating them internally. In this project, controllers
     don't create DbContext or TokenService themselves — they declare them in the
     constructor and the framework injects them. This makes testing easier (you
     can inject mocks) and ensures the right lifetime (scoped vs singleton) is
     respected.

  Q: What is the difference between Singleton, Scoped, and Transient?
  A: Singleton: one instance for the app lifetime (TokenService).
     Scoped: one instance per HTTP request (DbContext, SessionService).
     Transient: new instance every time it's requested.
     Getting this wrong causes bugs: e.g. injecting a Scoped DbContext into a
     Singleton would cause it to be reused across requests (data leaks).

  Q: Why is the JWT key stored as Base64?
  A: The key is raw bytes (e.g. 32 bytes = 256-bit key). JSON config files store
     strings, not binary. Base64 is the standard way to represent binary data as
     a safe printable string. At runtime, Convert.FromBase64String() reverses it.

[DB NOTE] Sessions table stores every active session token.
          Users table stores PasswordHash.

--- LOGIN FLOW (line by line) ---

POST /api/auth/login   receives { username, password }

1. Normalise username to lowercase, look up in DB by email OR username.
2. _passwordHasher.VerifyHashedPassword(user, user.PasswordHash, plaintext)
   → Returns Failed / Success / SuccessRehashNeeded
   SuccessRehashNeeded means the old hash format is outdated; re-hash and save.
3. Invalidate all previous active sessions for this user (single sign-on).
4. Build Claims array:
     ClaimTypes.Name            = user display name
     ClaimTypes.NameIdentifier  = user.UserId (used everywhere as the "uid")
     ClaimTypes.Role            = "0" or "1" or "2"
5. _tokenService.CreateToken() → JwtSecurityToken with
     Subject=userId, custom claims, Issuer, Audience, Expiry, HMAC-SHA256 sig
6. sessionService.CreateSessionAsync() → INSERT into Sessions table
7. Return { token, expiresAt }

--- TOKENSERVICE ---
  CreateToken():
    - Reads key from env var (overrides appsettings → env vars win in prod)
    - Decodes base64 → bytes → SymmetricSecurityKey
    - Creates JwtSecurityToken with all claims
    - JwtSecurityTokenHandler().WriteToken() serialises to the "xxxxx.yyyyy.zzzzz" string
    - Stores expiry in _lastExpiry field (singleton keeps this between calls)

--- SESSIONSERVICE ---
  CreateSessionAsync():
    1. Fetches ALL active sessions for this userId
    2. Marks them all IsActive=false (old sessions invalidated)
    3. Creates new Session row with the new JWT string
  IsSessionValidAsync():
    1. Looks up session by (userId, token, IsActive=true, ExpiresAt > now)
    2. Returns bool — used by ApiControllerBase.ValidateSessionAsync()
  InvalidateSessionAsync():
    Sets IsActive=false for the token → used on logout

--- MVC SIDE (AccountController) ---
  On successful login:
    1. Calls POST /api/auth/login to get the JWT
    2. Parses the JWT with JwtSecurityTokenHandler().ReadJwtToken()  (NO signature
       validation here — the API already validated it)
    3. Calls sessionService.InvalidateAllUserSessionsAsync() then
       sessionService.CreateSessionAsync() — the MVC app maintains its own
       session record too
    4. Stores JWT in an HttpOnly cookie named "ApiAccessToken"
    5. Signs in using ASP.NET Core Cookie Auth (HttpContext.SignInAsync)
       — this creates the browser authentication cookie

  HttpOnly cookie:
    - Browser sends it on every request automatically
    - JavaScript CANNOT read it (prevents XSS token theft)
    - Secure flag set when HTTPS is in use

  On subsequent requests (CreateAuthorizedClient):
    Reads the cookie → puts it in Authorization: Bearer <token> header of the
    HTTP call to the API.

POTENTIAL PROFESSOR QUESTIONS:
  Q: Why are there TWO sessions being tracked (one in APIPSI16, one in MVC)?
  A: The API session validates the JWT on every API call. The MVC session cookie
     authenticates the browser request to the Razor app. They hold the same token
     but serve different auth systems.

  Q: What is HMAC-SHA256 and why is it used for JWTs?
  A: HMAC-SHA256 is a symmetric signature algorithm (same key to sign and verify).
     It prevents anyone from modifying the JWT payload (e.g. changing Role from
     "1" to "0") without knowing the secret key.

  Q: How does the password hashing work?
  A: ASP.NET Core's PasswordHasher<T> uses PBKDF2 with HMAC-SHA512, 10,000
     iterations, and a random salt. The result is a base64 string stored in
     PasswordHash. VerifyHashedPassword extracts the salt from the stored hash
     and runs the same derivation on the input password to compare.

  Q: What is the RegisterRequest class and what validations does it have?
  A: It's a DTO with [Required], [EmailAddress], [MinLength(8)] on Password,
     and [RegularExpression] for PhoneNumber. Validation fires automatically
     because of [ApiController] — ModelState.IsValid is checked before the
     method body runs. If callerRole != "0", the Role field is forced to 1
     (prevents a non-admin from registering with admin role).

--- API SIDE ---

    var result = await ValidateSessionAsync();
    if (result != null) return result;

    Gets the HttpClient from IHttpClientFactory (named "Api")
    Reads the JWT cookie → sets as Bearer token header
    All API calls use this client

    Reads ClaimTypes.NameIdentifier from the cookie-auth principal

  IsAdmin():
    Checks ClaimTypes.Role == "0"

    Reads error response body without throwing — used to surface API errors
    to the MVC model state

POTENTIAL PROFESSOR QUESTIONS:
  Q: Why return null from ValidateSessionAsync instead of throwing an exception?
  A: Exceptions are expensive and are meant for exceptional conditions, not
     normal auth failures. Returning null (valid) or IActionResult (invalid)
     keeps it efficient. The caller checks and returns early if not null.

  Q: What is IHttpClientFactory and why use it instead of new HttpClient()?
  A: HttpClient should NOT be instantiated with new each time (causes socket
     exhaustion due to port reuse). IHttpClientFactory manages a pool of
     HttpMessageHandler instances that are reused safely.

SECTION 6 — OPPORTUNITIES + MATCH SCORING  [CRITICAL — read in Hour 4]
================================================================================

FILE: APIPSI16/Controllers/OpportunitiesController.cs
      XcelerateLinks/Controllers/OpportunitiesController.cs

--- API KEY ENDPOINTS ---

GET /api/opportunities
  Returns all opportunities. Include(o => o.Company) for name.

GET /api/opportunities/with-match
  For each opportunity, calculates a match score against the current user's
  preferences (job roles + location).
  Uses MatchScoreHelper:
    RoleScore    = F1 score(precision, recall) of role overlap * 100
    LocationScore = ComputeLocationScore() based on LocationId + Region + Country
    WeightedScore = roleScore * 0.7 + locationScore * 0.3
  Returns sorted by MatchScore desc.

POST /api/opportunities  [Authorize(Roles = "0,2")]
  Creates a new opportunity. Only admin (0) or employer (2) can create.
  After saving, calls NotifyPerfectMatchUsersAsync() — finds all job seekers
  with 100% match score and sends them a notification.

--- MVC SIDE ---
  Index() is role-dispatched:
    Admin → loads all via GET /api/opportunities → renders View (table)
    User/Employer → loads via GET /api/opportunities/with-match → UserIndex view
  Supports query filters: q (text search), locationId, employmentType, remoteOption
  Filters are applied IN MEMORY (after the API returns the list) because the
  /with-match endpoint returns a rich DTO that's already in memory.

POTENTIAL PROFESSOR QUESTIONS:
  Q: What is the MatchScore formula?
  A: It's a weighted combination:
       roleScore    = F1 score = 2 * matchCount / (userPrefCount + requiredRoleCount) * 100
       locationScore = 0–100 based on exact/region/country proximity
       final = roleScore * 0.7 + locationScore * 0.3
     If the opportunity has no required roles, only location is used (weight 1.0).
     If there is no location data, only roles are used (weight 1.0).

  Q: What is the F1 score and why use it for role matching?
  A: F1 = harmonic mean of precision and recall.
     Precision = fraction of user's preferences that match required roles.
     Recall = fraction of required roles that the user covers.
     Using only recall would give 100% when a user has ALL required roles even
     if they also listed 50 other roles. F1 penalises both overspecific and
     underspecific matches.

  Q: How does role-dispatching work in the MVC controller?
  A: The Index() method checks IsAdmin() (ClaimTypes.Role == "0").
     If admin, it fetches the admin endpoint and returns a different view.
     If regular user, it fetches the match endpoint and returns UserIndex view.
     This is a "poor man's role-based routing" — one URL, different experiences.

POTENTIAL PROFESSOR QUESTIONS:
  Q: What is SignalR and how does it differ from regular HTTP?
  A: SignalR is a library that provides a real-time bidirectional communication
     channel between server and browser. It uses WebSockets as the primary
     transport (falling back to Server-Sent Events or Long Polling). Unlike HTTP
     (request-response), the server can PUSH data to clients at any time.

  Q: What is a SignalR Group?
  A: A named set of connections. When you call Groups.AddToGroupAsync(), the
     connection is added to the group. Clients.Group("chat_5").SendAsync()
     delivers the message to all connections in that group simultaneously.
     This project uses groups "chat_{chatId}" and "user_{userId}".

  Q: Why is _userConnections a static ConcurrentDictionary?
  A: Hubs are transient (new instance per connection). To share state across
     all connections (e.g. know which users are online), it must be static.
     ConcurrentDictionary is thread-safe for concurrent Add/Remove operations
     from multiple connections.

  Q: What is ExecuteUpdateAsync and why use it instead of loading entities?
  A: ExecuteUpdateAsync translates directly to a single SQL UPDATE statement
     without loading any entities into memory. For mark-all-as-read, loading
     hundreds of messages just to set ReadAt would waste memory. Direct update
     is more efficient.

  Q: What is [ValidateAntiForgeryToken] and why is it on POST actions?
  A: It validates a hidden form field (_RequestVerificationToken) that ASP.NET
     generates per session. It prevents CSRF (Cross-Site Request Forgery) attacks

  Q: Why does Login parse the JWT on the MVC side without verifying the signature?
  A: The MVC app trusts that the API already validated the JWT before issuing it.

     It prevents Open Redirect vulnerabilities where an attacker crafts a
     returnUrl pointing to a malicious site and the app blindly redirects there.

SECTION 22 — JWT & COOKIES: SIMPLE REFERENCE  [CRITICAL — quick flip-back]
================================================================================

HOW IT ALL WORKS ON THIS SITE — THE SHORT VERSION
  You do NOT need to know implementation details. Know this story:

  1. You visit the login page and submit your username + password.

  2. The MVC app sends them to the API (/api/auth/login).

  3. The API checks the password, then creates a JWT token.
     The JWT contains: your userId, your username, your role, and an expiry.
     It is SIGNED with a secret key so nobody can fake or alter it.

  4. The API also saves a row in the Sessions table
     (Token, UserId, IsActive=true, ExpiresAt).
     This is so the site can revoke your login even before the JWT expires
     (e.g. when you log out from another device).

  5. The MVC app saves the JWT inside a cookie called "ApiAccessToken".
     Cookie settings:
       HttpOnly = true   → your browser's JavaScript CANNOT read it
                           (protects against XSS attacks stealing the token)
       Secure = true     → only sent over HTTPS
       SameSite = Lax    → not sent on cross-site form posts (CSRF protection)
       Expires in 1 hour → both the cookie and the JWT expire together

  6. From now on, every time your browser makes a request, it sends the
     cookie automatically. The MVC app reads the JWT out of the cookie and
     attaches it as:   Authorization: Bearer <token>
     when it calls the API.

  7. The API receives the request, validates the JWT (checks signature,
     checks expiry), then checks the Sessions table to make sure the
     session is still IsActive=true and not expired.
     If both pass → you are authenticated and your request goes through.

  8. When you log out:
     - The "ApiAccessToken" cookie is deleted from the browser.
     - The Session row in the DB is set to IsActive=false.
     - Even if someone had copied the JWT string, it is now invalid
       because the Sessions check will reject it.

  ─────────────────────────────────────────────────────────────────────────
  WHY TWO THINGS? (JWT + Sessions table)
  ─────────────────────────────────────────────────────────────────────────
  A JWT on its own is "stateless" — once issued, anyone with the token can
  use it until it expires. There is no way to revoke it early.

  The Sessions table makes it "stateful" — the server keeps a record of
  every active login. On logout, the record is marked inactive, so the JWT
  is immediately invalidated even though it hasn't expired yet.

  SHORT ANSWER FOR THE PROFESSOR:
    "The Sessions table gives us server-side revocation. JWTs alone can't
     be cancelled before their expiry time, but by checking the Sessions
     table on every request we can instantly log someone out."

  ─────────────────────────────────────────────────────────────────────────
  JWT STRUCTURE — what the 3 parts actually contain here
  ─────────────────────────────────────────────────────────────────────────
  Header   : { "alg": "HS256", "typ": "JWT" }
  Payload  : { "nameid": "42",              ← userId
               "unique_name": "john_doe",   ← username
               "role": "1",                 ← 0=Admin 1=User 2=Employer
               "exp": 1741999200 }          ← unix timestamp expiry
  Signature: HMAC-SHA256(base64(header) + "." + base64(payload), secretKey)

  ─────────────────────────────────────────────────────────────────────────
  COOKIE vs LOCALSTORAGE — why cookie is better here
  ─────────────────────────────────────────────────────────────────────────
  localStorage:  JavaScript CAN read it → XSS attack can steal the token
  HttpOnly cookie: JavaScript CANNOT read it → XSS cannot steal the token
  That is the only reason the JWT is stored in a cookie instead of
  localStorage. The cookie IS the security wrapper around the JWT.

Q1. Explain the two-project architecture. Why call the API instead of the DB directly?
A:  There are two ASP.NET Core projects. APIPSI16 is the REST API — it owns all
    business logic and talks to SQL Server via EF Core. XcelerateLinks is the MVC
    frontend — it renders Razor views and calls the API over HTTP using
    IHttpClientFactory. The DB is never exposed to the frontend. Separation of
    concerns means the API can be updated or reused (e.g. by a mobile app) without
    touching the frontend.

Q2. What DI lifetimes are used? Give examples.
A:  Three lifetimes:
      Singleton  — one instance for the whole app lifetime.
                   Example: ITokenService / TokenService (no DB context needed).
      Scoped     — one instance per HTTP request.
                   Example: ISessionService / SessionService (needs DbContext,
                   which is itself Scoped — never inject Scoped into Singleton).
      Transient  — new instance every time it is injected (rarely used here).

Q3. What is the purpose of the Sessions table alongside JWTs?
A:  JWTs are stateless — once issued, the server cannot cancel them before expiry.
    The Sessions table adds server-side revocation. On logout, the row is set to
    IsActive=false. Every API request then checks the Sessions table; if the session
    is inactive the request is rejected (401) even though the JWT signature is still
    mathematically valid. This makes logout actually work.

Q4. How does the login flow work end-to-end?
A:  1. User submits the login form → MVC POSTs credentials to POST /api/auth/login.
    2. API: finds user by email or username, verifies password with PasswordHasher.
    3. API: builds JWT (userId, username, role in payload), signs with HS256.
    4. API: saves a Session row (Token, UserId, IsActive=true, ExpiresAt).
    5. API: returns { token, expiresAt }.
    6. MVC: saves the JWT in the HttpOnly "ApiAccessToken" cookie.
    7. MVC: calls HttpContext.SignInAsync() to create the ASP.NET cookie identity.
    8. MVC: redirects to the requested page (LocalRedirect).

Q5. How does the MVC app pass the JWT to API requests?
A:  The TokenHandler (a DelegatingHandler registered on the named HttpClient "Api")
    intercepts every outgoing API call. It reads the "ApiAccessToken" cookie from
    the current HttpContext and injects it as the Authorization: Bearer <token>
    header. ApiControllerBase.CreateAuthorizedClient() does the same manually for
    controllers that build their own clients.

Q7. Why are RequiredJobRoleIds stored as a comma-separated string?
    What are the trade-offs?
A:  It is a simplicity trade-off. A junction table (OpportunityJobRoles) would be
    more normalised and support direct SQL JOINs, but requires extra migrations and
    more complex queries. The comma-string is simpler to write and read. The cost:
    filtering by role must be done in C# after loading data — no SQL WHERE on roles.

Q8. What is the UNIQUE INDEX on the Connections table and why is it there?
A:  UNIQUE INDEX on (RequesterUserId, AddresseeUserId). It prevents two Connection
    rows between the same pair of users at the DB level. The code also checks for
    an existing row in EITHER direction with AnyAsync() before inserting. The index
    is the last line of defence against race conditions (two simultaneous requests
    both passing the in-code check).

Q9. What is the difference between LocationId (FK) and Location (text field)?
A:  Location is a legacy free-text field (e.g. "Lisboa"). LocationId is a FK to
    the structured Locations table, which also holds Region and CountryId. The
    structured version lets MatchScoreHelper compare regions and countries precisely.
    Both are kept for backward compatibility with older data.

Q10. How are migrations applied at startup? What is the raw SQL safety-net for?
A:  Program.cs calls ctx.Database.Migrate() on startup, which runs all pending
    EF Core migrations. The raw SQL safety-net checks IF NOT EXISTS for specific
    columns (PriorityId, IsDiscarded) on EmployerCandidateHistory that were added
    outside of EF migrations and ALTERs the table if they are missing. It is a
    pragmatic fallback to keep the schema consistent even if a migration was missed.

AUTHENTICATION / SECURITY
────────────────────────────────────────────────────────────────────────────────

Q11. What is a JWT? What three parts does it have? What does each contain?
A:  JWT = JSON Web Token. Three dot-separated Base64-URL-encoded parts:
      Header    — algorithm and type: { "alg": "HS256", "typ": "JWT" }
      Payload   — claims: userId (nameid), username (unique_name), role, expiry (exp)
      Signature — HMAC-SHA256 of (header + "." + payload) using the secret key.
    The payload is readable by anyone; the signature makes it tamper-proof.

Q12. What algorithm signs JWTs here? Why is it symmetric?
A:  HS256 (HMAC-SHA256). Symmetric means the SAME secret key is used both to sign
    (at login) and to verify (on every API request). It is appropriate here because
    the same server both issues and validates tokens. The key is stored base64-encoded
    in an environment variable (XCELERATE_JWT_KEY) so it is never in source code.

Q13. How are passwords stored and verified?
A:  ASP.NET Core's PasswordHasher<T> uses PBKDF2 with HMAC-SHA512, a random salt,
    and 10,000 iterations. The result is stored in Users.PasswordHash as a base64
    string. On login, VerifyHashedPassword() extracts the stored salt, re-derives
    the hash from the supplied password, and compares. SuccessRehashNeeded means
    the parameters have been updated and the hash should be re-saved with the new
    settings.

Q14. What is CSRF? How does [ValidateAntiForgeryToken] prevent it?
A:  CSRF (Cross-Site Request Forgery): a malicious page tricks the browser into
    submitting a form to this site, because the browser automatically sends cookies
    with every request. [ValidateAntiForgeryToken] requires a hidden form field
    (_RequestVerificationToken) that ASP.NET generates per session. A cross-site
    request cannot know this token, so the check fails. The API does not need it
    because it uses JWTs (not cookies), so an attacker cannot set the Authorization
    header from another origin.

Q15. Why is the JWT stored in an HttpOnly cookie in the MVC app?
A:  Storing it in localStorage would expose it to JavaScript — any XSS attack could
    steal it. An HttpOnly cookie is never accessible to JavaScript; only the browser
    sends it (automatically on every request). Combined with Secure (HTTPS only) and
    SameSite=Lax (not sent on cross-site POSTs), this protects the token from both
    XSS theft and CSRF.

EF CORE
────────────────────────────────────────────────────────────────────────────────

Q16. What is the difference between .Include() and a new query?
A:  .Include(x => x.NavProp) generates a SQL JOIN and retrieves the related entity
    in the same database round-trip. A separate query means a second round-trip.
    Doing it inside a loop creates the N+1 problem — one extra query per parent row.
    Use .Include() when you always need the related data to avoid N+1 issues.

Q17. What does SaveChangesAsync() do internally?
A:  It takes all entities tracked by the DbContext that are in Added, Modified, or
    Deleted state, generates the corresponding INSERT/UPDATE/DELETE SQL, and runs
    them in a single database transaction. If any statement fails, the whole batch
    is rolled back automatically.

Q18. What is EntityState.Modified and when would you use it?
A:  Setting _context.Entry(entity).State = EntityState.Modified tells EF that ALL
    properties have changed, generating an UPDATE for every column. Used in
    UpdateCompany() where the whole entity is replaced. More efficient alternative:
    mark only specific properties as modified to generate a narrower UPDATE statement
    (avoids overwriting unchanged columns).

Q19. What is DbUpdateConcurrencyException and how is it handled here?
A:  Thrown when an EF UPDATE affects 0 rows — typically because another request
    deleted or modified the row between the GET and the PUT (optimistic concurrency).
    In UpdateCompany(): if CompanyExists() returns false, return 404 (the company
    was deleted). Otherwise re-throw as an unhandled exception (500).

Q20. What is .ExecuteUpdateAsync() and when should you use it?
A:  Translates directly to a single SQL UPDATE statement without loading any entities
    into the EF change tracker. Used in ChatController to mark all messages in a chat
    as read. Far more efficient than loading hundreds of message objects, setting
    ReadAt on each, and calling SaveChangesAsync() — especially for bulk operations.

Q21. What HTTP method and status code for a "duplicate application" error?
A:  POST with 409 Conflict. The resource — a job application for this specific
    (user, opportunity) pair — already exists, so the operation conflicts with the
    current state of the resource.

Q22. What is the difference between 401 Unauthorized and 403 Forbidden?
A:  401 Unauthorized — the request has no valid authentication (token missing,
    invalid, or session inactive). "Who are you? I don't know you."
    403 Forbidden — the user IS authenticated but lacks permission (wrong role,
    or trying to edit another user's data). "I know who you are, but no."

Q23. What is 429 Too Many Requests? When and why is it returned here?
A:  Returned when a Free plan user hits their quota: 5 job applications per calendar
    month, or 50 accepted connections. It signals a temporary limit, not a permanent
    denial (compare with 403 which means permanently forbidden). The client knows
    they can retry after upgrading their plan.

Q24. What is the purpose of the [ApiController] attribute?
A:  It automatically validates ModelState (returns 400 Bad Request if validation
    annotations fail, without needing `if (!ModelState.IsValid)` in every action).
    It also enables attribute routing inference and better binding source inference
    (body vs route vs query string params).

Q25. What is CreatedAtAction() and what status code does it return?
A:  CreatedAtAction() returns HTTP 201 Created. It also sets the Location response
    header to the URL of the newly created resource, constructed from the referenced
    GET action name and route values. This follows the REST convention: a successful
    POST should return 201 + a Location pointing to the new resource.

SIGNALR / REAL-TIME
────────────────────────────────────────────────────────────────────────────────

Q26. What is SignalR and when would you use it instead of regular HTTP?
A:  SignalR is a library that provides a persistent, bidirectional connection between
    browser and server, using WebSockets as the primary transport (falling back to
    Server-Sent Events or Long Polling). HTTP is request-response — the server can
    only respond when the client asks. SignalR lets the server PUSH data to clients
    at any time. Use it when data must be delivered instantly (chat, online status,
    notifications) and polling would be too slow or wasteful.

Q27. How does a user "join" a chat room in the Hub?
A:  In OnConnectedAsync(), the hub queries the ChatUsers table to find all chats the
    user is a member of. For each chat, it calls:
      Groups.AddToGroupAsync(Context.ConnectionId, "chat_{chatId}")
    Any message broadcast to "chat_5" is then delivered to all connected tabs of all
    participants of that chat.

Q28. Why is _userConnections a static field?
A:  Hub instances are created fresh per connection (transient lifecycle). A static
    field is shared across ALL hub instances in the process, so it persists as
    connections come and go. Without static, each connection would see an empty
    dictionary. ConcurrentDictionary is used for thread-safety because multiple
    connections can read/write simultaneously.

Q29. What is the difference between Clients.Group() and Clients.All()?
A:  Clients.All() sends to every connected SignalR client on the entire server.
    Clients.Group("chat_5") sends only to connections that have been added to that
    named group — i.e. participants of chat 5. This project uses Groups everywhere
    to scope messages to only the relevant users.

Q30. How does the "already have a Direct chat" idempotency check work?
A:  POST /api/chat/with-participants first checks the DB: is there already a Direct
    (2-person) chat containing exactly the same two participants? If yes, it returns
    the existing chatId instead of creating a new one. This makes "start a chat"
    safe to click multiple times — the same chat is always returned.

Q31. What is the Post-Redirect-Get pattern and why use it?
A:  After a successful form POST, instead of rendering a view directly, the server
    redirects the browser to a GET action. This prevents the browser from resubmitting
    the form when the user presses F5 (which would re-POST). TempData is used to pass
    a success message across the redirect because ViewBag does not survive redirects.

Q32. What is the difference between TempData and ViewBag?
A:  TempData["X"] is stored server-side (session/cookie) and survives exactly one
    redirect — it is cleared after being read. Used for POST-Redirect-Get messages.
    ViewBag.X is a dynamic dictionary valid only for the current request/response
    cycle — used to pass data from the current controller action to the view it
    renders directly.

Q33. Why must type="checkbox" be explicit for a bool? field?
A:  Without type="checkbox", asp-for renders a text input. A text input sends an
    empty string when blank and "on" when checked — neither of which binds to bool?.
    With type="checkbox", the browser sends "true" when checked and nothing (or the
    hidden input "false") when unchecked. The model binder then correctly converts
    "true"/"false" to bool?.

Q34. What does [ValidateAntiForgeryToken] do and where is it needed?
A:  On every POST action in the MVC app, it validates the hidden
    _RequestVerificationToken field that the form generated with @Html.AntiForgeryToken()
    or the asp- tag helpers. If the token is missing or wrong, the request is rejected
    with 400 Bad Request. Prevents CSRF attacks. NOT needed on the API because the
    API uses JWT Bearer tokens (not cookies) for authentication.

Q35. What is a Tag Helper? Give three examples from this project.
A:  Tag Helpers are server-side components that augment HTML elements in Razor views.
    They run at render time and modify the output HTML.
    Three examples:
      asp-for           — generates id, name, value from model expression + hooks up validation
      asp-controller + asp-action — builds correct href using MVC routing
      asp-route-id      — appends a route parameter (e.g. /opportunities/42) to a link

MATCH SCORING
────────────────────────────────────────────────────────────────────────────────

Q36. Explain the F1 score formula. Why use it instead of just recall?
A:  F1 = 2 * matchCount / (userPrefCount + requiredRoleCount) * 100
    matchCount = job roles that appear in BOTH the user's preferences AND the
    job's required roles.
    Using only recall (matchCount / requiredRoleCount) gives 100% if a user lists
    every possible role — it rewards over-listing. F1 is the harmonic mean of
    precision (how relevant the user's choices are) and recall (how much of the
    job they cover). It penalises both over-listing and under-listing.

Q37. What does MatchScoreHelper do for small vs large countries?
A:  ComputeLocationScore() distinguishes small compact countries (Portugal, Netherlands,
    Belgium, etc. — a HashSet for O(1) lookup) from large countries (US, Canada,
    Brazil). For a small country, a different region still scores 35 (still fairly
    close). For a large country, a different region scores 0 (effectively a different
    job market). Same region scores 65 (small country) or 50 (large country).
    Exact LocationId match = 100. Different country = 0. No data = -1 (excluded).

Q38. What weight does location have vs job roles? What if one is missing?
A:  WeightedScore = roleScore * 0.7 + locationScore * 0.3
    If the opportunity has NO required roles → only locationScore is used (weight 1.0).
    If there is NO location data (score = -1) → only roleScore is used (weight 1.0).
    The missing component is excluded and the remaining component takes the full weight.

Q39. How is the Free plan monthly application limit enforced?
A:  In JobApplicationsController.Apply():
      if (user.SubscriptionPlan == 0)  // Free plan
    It counts rows in JobApplications where UserId == uid AND
      AppliedAt >= new DateTime(UtcNow.Year, UtcNow.Month, 1, 0,0,0, Utc)
    (i.e. the first day of the current month in UTC).
    If the count is >= 5, return 429 Too Many Requests.
    The same pattern enforces the 50-connection limit in ConnectionsController.

Q40. Why use HTTP 429 for subscription limits rather than 403?
A:  403 Forbidden means permanently not allowed — wrong role or permission. It
    implies the user can NEVER do this. 429 Too Many Requests signals a quota/rate
    limit that is temporary — the user CAN do this in principle, but not right now
    on their current plan. It semantically communicates "try again after upgrading"
    rather than "this is always denied."
